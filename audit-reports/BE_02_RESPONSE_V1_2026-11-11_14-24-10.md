## High

**BE-SEC-101: the login lockout can be bypassed on qa, and maybe on production** ⏳ Deferred: to be fixed before going live
- **Problem:** the server counts wrong passwords by the visitor's internet address. It reads that address from a header (`X-Real-IP`) that the web server in front is supposed to write. On qa, Django can also be reached directly on its port, with nothing in front to write the header. So anyone can write a new fake address on every try, and the "5 wrong passwords, blocked 15 minutes" rule never triggers. That means unlimited password guessing, including against Super Admins. Production is safe only if the panel's web server always overwrites the header. That is not in our code and could not be checked.
- **Plan (about 20 lines plus tests):** believe the header only when the request really comes from our own web server on the same machine, and only when it holds a real address. Production, and qa through its domain, keep working as today. No API change.
- **What happened:** the lead approved it and it was built and merged (PR #112, commit `6c2bcc4`, 2026-11-19). On 2026-11-20 the lead decided it is not needed in this phase, and it was reverted (commit `8c351fd`), together with the per-IP limits (PR #119). **This is deferred work, not an accepted risk:** it must be fixed before going live. Putting it back is mostly undoing the revert, with its tests.
- **Until then:** set `TRUST_X_REAL_IP=False` in the qa settings file and restart.
- **Production team:** confirm the panel's web server writes `X-Real-IP` with the visitor's real address, also behind Cloudflare.
- **Django admin, done (PR 12, lead's decision of 2026-11-11):** the most exposed login is gone: `/django-admin/` is switched off on every server and answers 404. It stays on developers' laptops only. The fix above is still needed for the app and console logins.

**BE-SEC-001: full email and mobile numbers in the audit log** ✅ Fixed (`fix/audit-personal-data`, BE_01 PR 1)
- **Problem:** editing an official saved their full email and mobile number in the audit log for good.
- **What we did:** masked in new entries, hidden in old entries by a one-time database update, plus a safety net in the one function that writes audit entries. See the BE_01 response.

**BE-SEC-002: a citizen could read another phone's service requests** 🟡 Partly fixed (`fix/citizen-own-requests`, BE_01 PR 7)
- **Problem:** the server believes the Android ID the app sends. Sending another phone's ID showed its requests, and sending a new ID got around a block.
- **What we did:** a phone sees only the requests made from its own install.
- **Left:** getting around a block stays possible until Play Integrity is switched on, after the app is on Google Play (owner's decision of 2026-11-04).

## Medium

**BE-ARC-101: some changes could be saved without their audit entry** ✅ Fixed (PR 1)
- **Problem:** changing the platform settings, a category or a notification text saved the change first and wrote the audit entry afterwards, separately. If the second step failed, the change stayed with no record of who made it. The project rule says both must be saved together.
- **What we did:** each change and its audit entry are now saved in one step (one database transaction): both or neither.
- **Proof:** 4 tests make the audit step fail and check that the change was not kept. All 4 fail on the old code.

**BE-REL-101: a post for many areas could notify people twice** ✅ Fixed (PR 2)
- **Problem:** one background job sends a new post to the notification topic of each of its areas, up to 200. When Firebase is slow, that job could run past its 120-second limit. The job system then stops it and runs it again from the start, so phones in the areas already done got the same post twice, at high priority.
- **What we did:** after 60 seconds the job starts no new area and hands the remaining areas to a new job. It never reaches the limit, so it is never re-run. Normally it finishes everything at once. Publishing still costs the same however many areas a post has.
- **New setting:** `PUSH_TOPICS_JOB_SECONDS` (60; must stay below 120).

**BE-ERR-101: wrong inputs crashed the server** ✅ Fixed (`fix/bad-input-400`)
- **Problem:** 24 kinds of wrong input gave a server error (500), six of them on public pages. Examples: a number written as `²`, an impossible date, an ID that is not an ID, or a broken CSV file.
- **What we did:** they now answer `400` or `404` with a clear message. Telugu digits still work.

**BE-ERR-102: a slow video check crashed the upload** ✅ Fixed (`perf/video-time-limits`, BE_01 PR 10)
- **Problem:** a video check that ran out of time was not caught, so the upload crashed after holding a server worker for minutes.
- **What we did:** short time limits per step; a video over them is refused like an unreadable one.

**BE-ERR-103: an outage at Google gives a server error at citizen registration** ✅ Fixed (PR 10)
- **Problem:** if Google's Play Integrity service cannot be reached, registering a new phone crashes with a 500 instead of a clear answer.
- **What we did (decision of 2026-11-11):** the server now answers `503 integrity_unavailable`, "The phone check is not available right now. Try again in a few minutes.", with `retry_after_s` 60 and the `Retry-After` header. Nothing is stored and the challenge is not used up, so the app can try again with it. A refused check still answers `403 integrity_failed`.
- **Today:** Play Integrity is switched off on production, so this only matters once it is switched on.
- **Mobile team:** show this new answer as "try again later".

**BE-COR-101: the dashboard showed the wrong escalation hours** ✅ Fixed (`perf/request-path`, BE_01 PR 4)
- **Problem:** the dashboard read the setting under the wrong name, so it always showed the default 24 hours.
- **What we did:** it reads the setting the Super Admin saved.

**BE-COR-002: two saves at the same moment could crash** 🟡 Partly fixed (`fix/api-errors-and-races`, BE_01 PR 2)
- **What we did:** the second save now gets "already used" instead of a crash.
- **Left on purpose:** two citizen posts at the very same instant can let one extra post past the daily limit, which is acceptable for a soft limit.

**BE-SEC-102: an admin's post goes straight out to any area** ⚪ Not changed, on purpose
- **Why:** owner's decision of 2026-10-28: anyone who may post may post anywhere, and admins' posts publish at once. The audit finding is withdrawn.

**BE-SEC-008: Django admin could get around the safety rules** ✅ Fixed (`fix/audit-personal-data`, BE_01 PR 1)
- **What we did:** no password setting or blocking in Django admin, and every other change there is audited.

**BE-SEC-006: no limit on how often public pages can be called** ⚪ Not changed, on purpose
- **Why:** decided (2026-11-10) to add no limits on token refresh, citizen challenge and device registration, and no limit on new phones per address. Mobile networks put many phones behind one address, so such limits could block whole villages.
- **Since 2026-11-20:** the per-IP limits that did exist (the web server's request limits, the login throttle, the cap on failed logins per address, the contact form's limit) were removed by the lead's decision, "not needed in this phase". Deferred, not accepted: to be put back before going live, with BE-SEC-101.

**BE-PERF-003: citizen posts with many videos can keep the server busy** ✅ Fixed (`perf/video-time-limits`, BE_01 PR 10)
- **What we did:** all files of one request share a 90-second checking budget, and the server's request limit is 120 seconds.
- **Since 2026-11-13:** the lead replaced "any number of photos and videos" with **up to 3 photos or one video per post**, never both, for everyone who posts (PR #92). Photos at most 10 MB, the video at most 60 MB, and at most 60 seconds since 2026-11-14 (`400 video_too_long`). One request now carries at most one short video.

**BE-CFG-101: upload size and time limits did not match between layers** ✅ Fixed (`perf/video-time-limits`, `fix/api-errors-and-races`)
- **Problem:** the app server allowed 300 seconds per request but the web server gave up after 60, and the village import had no size limit.
- **What we did:** both now allow uploads and imports 120 seconds, and the village import refuses files over 20 MB.
- **Production team:** let the panel's web server allow uploads and imports at least 120 seconds.

**BE-SEC-003: production runs on the hosting panel, outside our server setup** 🟡 Partly fixed (BE_01)
- **What we did (BE_01):** corrected the deploy guide, and decided to protect Django admin with the login lockout instead of an office address list.
- **What we did (BE_02, PR 12):** the lead decided to switch Django admin off on every server, so it no longer depends on the panel's web server or on the lockout.
- **Left:** the panel's other web server settings (`X-Real-IP`, upload time, body size) are the production team's.

**BE-SEC-005: a stranger could switch off an official's notifications** 🟡 Partly fixed (`fix/api-errors-and-races`, BE_01 PR 2)
- **What we did:** a stranger can no longer delete an official's phone registration (`409 duplicate`).
- **Not changed, on purpose:** when a second official logs in on the same phone, the phone moves to them (decision of 2026-11-10). This is needed for shared or handed-over phones, and logging out removes the phone first.

**BE-SEC-007: the audit log saved whatever was typed as a username** ✅ Fixed (`fix/audit-personal-data`, BE_01 PR 1)
- **What we did:** only the first letter is kept for unknown usernames, and old entries were hidden too.

**BE-PERF-001: posting was slow when many officials had to be notified** ✅ Fixed (`perf/request-path`, `fix/notification-fanout`)
- **What we did:** a fixed number of database steps for all officials together.

**BE-PERF-002: the dashboard and reports got slower with every district** ✅ Fixed (`perf/request-path`, `fix/db-report-queries`)
- **What we did:** a few database questions per page, whatever the number of districts.

**BE-SEC-004: production backups were not encrypted and stayed on the same server** ✅ Fixed (`fix/deploy-scripts`, BE_01 PR 6)
- **What we did:** encrypted backups and an off-site copy once they are configured.
- **Later:** where the copies go and who keeps the passphrase is to be decided after everything else (2026-11-10).

**BE-OBS-101: server errors and stopped background jobs go unnoticed** 🟡 Partly fixed (PR 11, PR 7)
- **Problem:** no error-tracking service, no request numbers to connect a user's report to the server log, and failed background jobs are visible only in Django admin.
- **What we did (decision of 2026-11-11: no outside service):**
  - Every answer carries a request number in the `X-Request-ID` header, and every server log line written for that request shows the same number, like `[3f9c…]`.
  - A server error (500) also gives the number in its message, so the console or app can show it and a user can quote it. The developer then finds the exact log lines.
  - The health check shows whether background jobs run (BE-REL-103, PR 7).
  - No new package, and nothing leaves the server.
- **Left:** nobody is alerted automatically when errors happen. An error-tracking service such as Sentry would do that, but it needs the owner's approval (outside service, cost).

**BE-TEST-001: tests could touch a real database** ✅ Fixed (`fix/settings-and-ci`, BE_01 PR 3)

**BE-CI-001: the tests did not run automatically on GitHub** 🟡 Partly fixed (`fix/settings-and-ci`, BE_01 PR 3)
- **What we did:** every pull request into `dev` runs all tests and the database check.
- **Not changed, on purpose (decision of 2026-11-11):** the checks stay on `dev` only. Code reaches `qa` and `main` by promotion from `dev`, where it was already tested; a fix merged straight into `qa` or `main` is not tested automatically.

**BE-DP-101: no rules for how long personal data is kept** ⚪ Not changed, on purpose
- **Why:** decided (2026-11-10) to keep the data, confirmed as "data is kept permanently" on 2026-11-14 (lead's decision).
- **Nothing is hidden by age since 2026-11-20** (owner's decision): the audit log, website contact messages and service requests list every record, however old, page by page. Dates and filters only narrow a list. The 90- and 180-day windows described further down were removed (`AUDIT_VISIBLE_DAYS`, `CONTACT_MESSAGES_VISIBLE_DAYS`, `SERVICE_REQUEST_CLOSED_VISIBLE_DAYS` and `closed_visible_days` are gone). Only expired sessions and tokens, failed background jobs, old failed-login records and read notifications are cleaned up.
- **By design, nothing is deleted:** service requests, posts and services are never deleted. Completed, rejected, discarded and taken-down items stay as the record (confirmed 2026-11-11):
  - A citizen's service request goes to the village's Village Admin. Officials above them see it and can reassign it. The official moves it through New, Approved, In progress, then Completed or Rejected, and every step is kept as history and in the audit log.
  - Completed and rejected requests stay, so the citizen still sees the outcome, officials can look back, and reports count them.
  - Posts are discarded or taken down, never deleted (only an author's own unsubmitted draft can be deleted). Services are switched off, never deleted.
  - The Super Admin hides or closes items that are no longer used; there is no delete button for these, and none is planned.
- **Replaced on 2026-11-20, kept here as history. Shown for a while, then kept out of the lists, like the audit log** (decision of 2026-11-11, branch `feature/closed-items-window`):
  - Service requests: open ones always show. A completed or rejected request shows in the officials' lists (console and app) for 180 days after its last change (`SERVICE_REQUEST_CLOSED_VISIBLE_DAYS`). After that it stays in the database, still opens by its link, and shows again if anything changes on it. The citizen's own list is not affected.
  - The service-request list tells the console and app the number of days (`closed_visible_days`), so they can say so on screen. No database change; 7 new tests.
  - Website contact messages: the console shows the last 90 days (`CONTACT_MESSAGES_VISIBLE_DAYS`, owner's decision of 2026-11-11, branch `feature/contact-messages-window`); older ones stay in the database.

## Low

**BE-SEC-107: anything sent when editing a category went into the audit log** ✅ Fixed (PR 3)
- **Problem:** editing a category saved the whole request in the audit log as it was sent: unknown fields, any size. The audit log is never cleaned, so a client could fill it with anything.
- **What we did:**
  - Only the fields the server accepted and checked are saved.
  - As a safety net, any text in an audit entry is cut at 2,000 characters, with "…" at the end (new setting `AUDIT_TEXT_MAX_CHARS`).
  - Reviewers' comments and service-request notes are kept, as decided. The app already limits them to 500 characters, so they are never cut.

**BE-SEC-105: a notification text could break every notification of its kind** ✅ Fixed (PR 4)
- **Problem:** when the Super Admin changed a notification text, only the variable names were checked:
  - a single `{` crashed the save with a server error;
  - `{}` broke every notification sent with that text;
  - `{title:>999999999}` made each notification build a text of about 1 GB.
- **What we did:** only plain `{name}` variables from the list are accepted. Anything else answers `400` with a clear message, and nothing is saved. The 11 built-in texts are unaffected, and the API contract says so.
- **Web developer:** the console already shows this kind of error for unknown variables. Nothing to change, but good to know.

**BE-SEC-106: full mobile numbers in Django admin's history** ✅ Fixed (PR 5, and BE_01 PR 1)
- **Problem:** a website contact message showed as "name (full mobile) date". Django admin keeps that label in its change history, which is never cleaned.
- **What we did:** the label now shows `******3210`. The important numbers (contacts) were already fixed in BE_01 PR 1.

**BE-SEC-108: personal data sent to outside services or kept in logs** 🟡 Partly fixed (PR 6)

- **Not changed, on purpose:** Telugu name suggestions keep sending officials' English names to Google (decision of 2026-11-10). It should be mentioned in the privacy notice.
- **Left:** a citizen's name is part of the notification text stored with each background job (service-request notices to officials, `apps/notifications/services.py`). The branches that blocked it are merged; the change itself is still to do (BVTGC-16).

**BE-REL-103: a stopped background worker was invisible** ✅ Fixed (PR 7)
- **Problem:** if the background worker stops, no notifications, escalations or translations happen, but the health check still said "ok".
- **What we did:** the health check (`/api/v1/health/`) now also says `"worker": "ok"`, `"late"` or `"not_scheduled"`. It still answers "ok" with code 200, because the deploy scripts call it before they start the worker. The RUNBOOK explains what "late" means.

**BE-TEST-101: some important situations had no test** 🟡 Partly fixed (PR 8, and BE_01 PR 1)
