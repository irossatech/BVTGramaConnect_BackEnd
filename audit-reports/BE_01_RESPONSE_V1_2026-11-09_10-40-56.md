**Two extra bugs found while fixing.**
- The console's dashboard and its review-time report always showed 24 hours for escalation, whatever
  the Super Admin had set. They read the setting under the wrong name. Fixed in PR 4.
- A video check (ffprobe or ffmpeg) that ran out of time was not caught: the upload crashed with a
  server error (500) after holding a server worker for up to 3.5 minutes. Fixed in PR 10.

**One extra item from the audit's inventory.** The audit noted that the two sample-data commands
(`seed_sample_data`, `load_demo_area`) had no production guard. Run on a live server by mistake, they
would add a fake Super Admin, fake places and fake published posts. They now refuse on any server
(`DEBUG` off) unless `--allow-server` is given; the qa deploy script passes it for `SEED=1`, and
production never does. `create_super_admin`, used to make the real first Super Admin, is unchanged.
Fixed in PR 9.

## High

**BE-SEC-001: full email and mobile numbers in the audit log** ✅ Fixed (PR 1)
- **Problem:** when an official's details were edited, the audit log saved their full email and mobile
  number in each entry's details (`data`). The audit API (`/api/v1/audit/`) sent those details in full
  to anyone with a Super Admin login, and they stayed in the database and every backup for good. The
  console screen and the CSV export never showed this part, so they were not affected.
- **What we did:**
  - The audit log now saves only what changed, with email and mobile hidden: `r***@example.in`,
    `******3210`.
  - Old entries that already held full numbers are hidden too, by a one-time database update.
  - A safety net inside the one place that writes audit entries (`record()`): any email, mobile or
    phone is hidden and any password, token or secret is removed before saving, even if a future
    feature forgets to do it.

**BE-SEC-002: a citizen could read another phone's service requests** 🟡 Partly fixed (PR 7)
- **Problem:** the app tells the server the phone's Android ID, and the server believes it. Someone
  sending another phone's ID could see that phone's service requests: name, phone number, address.
  Someone could also get around a block by sending a new ID.
- **What we did:**
  - A phone now sees only the requests made from its own install, so nobody can read someone else's
    details this way.
  - Blocks and the daily limit still cover every install of a phone.
- **Left:** getting around a block stays possible until Play Integrity is switched on, after the app is
  on Google Play (owner's decision of 2026-11-04).

## Medium

**BE-SEC-003: Django admin may be open from anywhere on production** ✅ Fixed (PR 5, then `fix/django-admin-off`)
- **Problem:** `/django-admin/` is supposed to open only from the office. Production runs on a hosting
  panel whose web server settings we cannot see.
- **What we did:**
  - Corrected the deploy guide, which wrongly said production uses our own server setup.
  - First decided (2026-11-09) to rely on the existing lockout, with no office IP list.
  - **Then switched Django admin off on every server** (lead's decision of 2026-11-11, merged
    2026-11-12): `/django-admin/` answers 404 on qa and production and stays on developers' laptops only
    (`DJANGO_ADMIN_ENABLED`). Nothing is left to protect there.

**BE-SEC-004: production backups were not encrypted and stayed on the same server** ✅ Fixed (PR 6)
- **Problem:** the nightly backup holds password hashes and personal data, stored in plain form on the
  same server. Losing the server would lose the backups too.
- **What we did:**
  - The backup script now encrypts both backup files once a passphrase file exists.
  - It copies them to another place when one is configured.
  - It warns on every run until both are set up.
  - The guide explains how to set this up and how to restore.
- **Production team:** create the passphrase and the off-site copy.

**BE-SEC-005: a stranger could switch off an official's notifications** ✅ Fixed (PR 2)
- **Problem:** anyone who knew an official's phone push token could delete that phone's registration,
  and the official would silently stop getting notifications.
- **What we did:** the server now refuses that change with `409 duplicate`, and the official's device
  stays.

**BE-SEC-006: no limit on how often public pages can be called** ⚪ Not changed, on purpose
- **Problem:** pages that need no login (feed, village search, new-phone registration) have no request
  limit inside the app.
- **Why not changed:** mobile networks put thousands of phones behind one internet address. A per-address
  limit would block whole villages. The web server already limits each address to 20 requests a second.
- **Since 2026-11-20:** the per-IP limits that did exist were built and then removed (lead's decision of
  2026-11-20, "not needed in this phase"): the web server's 20 requests a second, the login throttle (30
  an hour per address), the cap of 50 failed logins an hour per address, and the contact form's 5 an
  hour. **Deferred, not accepted:** they are to be put back before going live, together with the
  BE-SEC-101 fix of BE_02. The per-username lockout (5 tries, 15 minutes) still runs.

**BE-SEC-007: the audit log saved whatever was typed as a username** ✅ Fixed (PR 1)
- **Problem:** for a failed login with an unknown username, the exact text typed was saved. If someone
  typed their password into the username box, the password was saved.
- **What we did:**
  - For unknown usernames only the first letter is kept (`g***`). Old entries were hidden too.
  - The lockout tables (django-axes) kept the typed text for 30 days as well. They now store a
    scrambled code (a keyed hash) instead; a one-time database update converted the rows already
    there. Lockout and Unlock work as before.

**BE-SEC-008: Django admin could get around the safety rules** ✅ Fixed (PR 1)
- **Problem:** a password changed in Django admin did not log the user out of the app, and changes made
  there were not audited.
- **What we did:**
  - Passwords can no longer be set in Django admin; it points to "Reset password" in the console, which
    logs the user out everywhere.
  - Blocking is no longer possible there.
  - Every other change there is now audited, with email and mobile hidden.
  - Service requests and citizen blocks are view-only there.

**BE-COR-001: some wrong inputs crashed the server** ✅ Fixed (PR 2)
- **Problem:** a wrong ID in a search filter, such as `?actor=abc`, gave a server crash (500) instead of a
  clear error.
- **What we did:** it now answers `400` with a clear message.

**BE-COR-002: two saves at the same moment could crash** 🟡 Partly fixed (PR 2)
- **Problem:** creating the same user, service or bill twice at the same moment gave a crash.
- **What we did:** the second one now gets a proper answer: "already used".
- **Left on purpose:** two citizen posts sent at the very same instant can let one extra post past the
  daily limit. That is acceptable for a soft limit.

**BE-PERF-001: posting was slow when many officials had to be notified** ✅ Fixed (PR 4)
- **Problem:** for every official to notify, the server did several separate database steps while the
  person posting waited.
- **What we did:** the server now does a fixed number of steps for all of them together. A test proves
  21 officials cost the same as 1.

**BE-PERF-002: the console dashboard and reports got slower with every district** ✅ Fixed (PR 4)
- **Problem:** the reports asked the database once per district and once per mandal: hundreds of
  questions for one page.
- **What we did:** a few questions in total now, whatever the number of districts. This is where the
  escalation-hours bug was found and fixed.

**BE-PERF-003: citizen posts with many videos can keep the server busy** ✅ Fixed (PR 10)
- **Problem:** at the time of the audit a citizen post could have any number of photos and videos,
  each checked while the phone waits. A slow or broken video could hold one of the 3 server workers
  for minutes.
- **What we did:**
  - Each video check has a short time limit (15, 20 and 45 seconds, before 30, 60 and 120). A video
    that takes longer is refused like an unreadable one, instead of crashing the request.
  - All photos and videos of one request share a 90-second budget. A post over it is refused with a
    clear message, and nothing is stored.
  - Since 2026-11-13 (lead's decision, PR #92) every post, citizen or official, has **up to 3 photos
    or one video**, never both: photos at most 10 MB each, the video at most 60 MB. Since 2026-11-14
    (lead's decision) the video is also at most 60 seconds (`400 video_too_long`).
    So one request now carries at most one short video, which makes this risk much smaller.
  - The server's request time limit is 120 seconds instead of 300.
  - Videos are still checked while the phone waits, so the citizen gets an answer at once. Moving
    this to the background would need a change in the app. Normal videos take a few seconds.

**BE-CI-001: the tests did not run automatically on GitHub** ✅ Fixed (PR 3)
- **Problem:** GitHub only ran security scans, never the 2,800+ tests, so a broken change could be merged.
- **What we did:**
  - Every pull request into `dev` now runs all tests and the database check, on Python 3.12 and 3.13.
  - GitHub actions are pinned to fixed versions.
- **Repo admin:** make these checks required in the `dev` branch settings.

**BE-TEST-001: tests could touch a real database** ✅ Fixed (PR 3)
- **Problem:** on a server set to production mode, running the tests would have used the real database
  and the real uploaded files.
- **What we did:** tests now always use a separate test database and test folder, whatever the settings say.

**BE-DOC-001: documents said different things than the code** ✅ Fixed (PR 3, PR 5)
- **Problem:** the shared project rules said the Super Admin cannot post (wrong since 2026-11-04). The
  architecture notes described push priority and test mode wrongly.
- **What we did:**
  - Corrected the notes.
  - Replaced the backend's out-of-date copy of the shared project rules with the current copy from the
    web repo, so they match again.
  - Corrected "Play Integrity on" for production: it is required by default, but the hosting panel
    keeps it off until the app is on Google Play (owner's decision of 2026-11-04).
- **Mobile team:** confirm the app repo's copy of the shared project rules matches.

## Low

**BE-SEC-009: a missing setting could put production into debug mode** ✅ Fixed (PR 3)
- **Problem:** if the server's settings file lost its `DEBUG=False` line, the site started in debug mode,
  which shows internal details to visitors.
- **What we did:** debug mode now refuses to start on a real web address, so the site stops instead of
  exposing details.
- **Production team:** make sure their settings file says `DEBUG=False`.

**BE-SEC-010: test mode could switch on by accident** ✅ Fixed (PR 3)
- **Problem:** the server went into test mode (weak password storage, no notifications) whenever the test
  tool was loaded.
- **What we did:** test mode now switches on only during a real test run.

**BE-SEC-011: the deploy script updated the code before checking it** ✅ Fixed (PR 6)
- **Problem:** the deploy script installed the new code first and checked it afterwards. A failed check
  left the bad version in place.
- **What we did:**
  - Packages are checked for known security holes before anything changes.
  - If the safety check fails, the previous version is put back automatically.

**BE-SEC-012: the server's deploy account has full admin rights** ⚪ Not changed, on purpose
- **Problem:** on servers built with our setup script, the deploy account can do anything without a
  password.
- **Why not changed:** with limited rights and no password, nobody could become admin on the server at
  all. The guide now explains the safer setting. Production does not use this script.

**BE-SEC-013: phone numbers in search links can reach server logs** ⚪ Not changed, on purpose (risk accepted)
- **Problem:** console searches such as `/users/?q=9876543210` put the number in the link, and a web
  server may write links into its log files.
- **Why not changed:** our own code never logs it, and only Super Admins use these searches. Accepted as
  a known risk on 2026-11-11; the production team's web server logs are left as they are.

**BE-SEC-014: Play Integrity did not check who signed the app** ✅ Fixed (PR 8)
- **Problem:** a copy of our app re-signed by someone else could pass the check.
- **What we did:** the server now also checks the app is signed with our key. It applies once Play
  Integrity is switched on.
- **Production team:** before switching it on, add Google Play's signing key to `ANDROID_CERT_SHA256`.

**BE-SEC-015: one limit was counted separately in each server process** ✅ Fixed (PR 5)
- **Problem:** the limit on Telugu name suggestions (60 a minute) was counted separately by each server
  process, so the real limit was several times higher.
- **What we did:** all processes now share one count.

**BE-SEC-016: a wrong error code revealed hidden items** ✅ Fixed (PR 2)
- **Problem:** asking for an item outside your area could answer "not allowed" instead of "not found",
  which hints that it exists.
- **What we did:** it now answers "not found", as the project rules say.

**BE-COR-003: deleted drafts left their video files behind** ✅ Fixed (PR 2)
- **Problem:** deleting a draft post removed its photos but not its video file (up to 50 MB each at the time; 60 MB since 2026-11-13).
- **What we did:** the video file is deleted too.

**BE-PERF-004: the contacts CSV import was very slow** ✅ Fixed (PR 4)
- **Problem:** a 5,000-row file meant about 30,000 database questions.
- **What we did:** a few dozen questions now, with the same checks.

**BE-PERF-005: failed notifications made the background worker wait** ✅ Fixed (PR 4)
- **Problem:** when Firebase failed, the worker paused (1 second, then 4) before trying again, holding up
  other jobs.
- **What we did:** the retry is now scheduled for later, and the worker never waits. Notifications for
  one event also share one Firebase connection.

**BE-PERF-006: the area tree loads all villages** ✅ Fixed (PR 4 and the web team)
- **Problem:** the console's area screen loaded all ~18,000 villages at once.
- **What we did:** village counting is now done by the database, which is much faster.
- **Web team:** the console now loads villages one mandal at a time (2026-11-11).

**BE-PERF-007: searches may get slow with lots of data** ⏳ Later
- Needs measuring on real data first.

**BE-OPS-001: backup gaps on servers built with our setup script** ⏳ Later
- To fix during the staging server setup. Production does not use this script.

**BE-OPS-002: server security settings could be tighter** 🟡 Partly fixed (PR 6)
- **What we did:** the web server no longer shows its version, and the security headers now cover every
  file type.
- **Left:** a stricter sandbox for the app service needs testing on a real server first.

**BE-OPS-003: the setup script claimed an Ubuntu version that cannot run the app** ✅ Fixed (PR 6)
- **Problem:** Ubuntu 22.04 has Python 3.10, but the app needs 3.12.
- **What we did:** the script now stops with a clear message, and the guide says Ubuntu 24.04.

**BE-API-001: the API documentation (Swagger) had errors** ✅ Fixed (PR 5)
- **Problem:** 28 errors and 30 warnings: some pages had no description, and two items had the same name.
- **What we did:** now 0 errors and 2 harmless warnings. A test keeps it that way.

**BE-API-002: the API contract listed pages that do not exist** ✅ Fixed (PR 5)
- **Problem:** two endpoints in the contract did not exist, and the health check was not listed.
- **What we did:** the contract is corrected.

**BE-CFG-001: the village import had no file-size limit** ✅ Fixed (PR 2)
- **What we did:** files over 20 MB are now refused with a clear message.

**BE-DOC-002: the deploy guides had mistakes** ✅ Fixed (PR 5)
- **What we did:** corrected a wrong file name, a wrong build step, a guide that contradicted itself, an
  old comment and a typo.

**BE-TEST-002: the load test covers only a little** ⏳ Later
- Needs the owner's expected number of users first.
