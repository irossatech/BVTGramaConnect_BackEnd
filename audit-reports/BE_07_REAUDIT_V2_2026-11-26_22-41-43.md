The code base is markedly better than at BE_02 and BE_03. Of 92 earlier findings, 47 are fixed, 26 partially fixed, 17 still open (6 of them by an accepted owner or lead decision), 2 no longer applicable, and none regressed in code.

The full test suite passes on SQLite (5,142 passed, 14 skipped). CI now also runs it on MariaDB 11.4 and PostgreSQL 17 with real-thread concurrency tests. The single-writer rules hold across 187 commits since 2026-11-09:
- post status changes only in `apps/posts/services.py`;
- audit only through `record()`;
- permission checks only through `authz`.

For Sprint 1 (Phase 1 release), the remaining risk sits in four places:
1. **The way production is actually run.** Production runs through the qa scripts on a hosting panel: 3 sync runserver/Gunicorn workers, a cron keep-alive and a hand-configured panel Nginx. None of the hardened templates in `deploy/` apply there. Nothing in the repo shows the rate limits, upload limits or headers are set there.
2. **Citizen registration with no throttle and no device attestation.** It relies on a client-sent `android_id` while Play Integrity is off, so post limits and blocks can be escaped. This is an accepted risk.
3. **A new correctness bug found in this audit:** escalation can stall permanently once 200 or more "Everyone" or state-level posts are pending (BE-DB-201). A public input can also break the Super Admin dashboard (BE-ERR-201).
4. **No error tracking or alerting, and backups that may be unencrypted, on-host only, and without the keys needed to restore citizen identity.**

**Conditions for the Phase 1 go-live (28 Nov):**
- BE-DB-201 and BE-ERR-201 fixed (both effort S);
- the panel Nginx and worker settings written down and verified against `deploy/templates` (BE-OPS-201);
- an error tracker and uptime alert in place (BE-OBS-201);
- backups encrypted, off-site, and the keys escrowed (BE-OPS-202, BE-OPS-203);
- `WALLET_ENABLED` kept off. The wallet's own findings (Appendix A) belong to Sprint 2.

### Medium

**BE-DB-202: Wallet entries insert before locking the wallet row (the MariaDB deadlock again); welcome-bonus limit races**
- Severity: Medium · Effort: S
- Evidence:
  - `apps/wallet/services.py:45-55`: INSERT of a WalletEntry with an FK to the wallet, then UPDATE of that wallet.
  - Called from `start_referral` (`:98-102`) inside sign-up's transaction (`apps/citizens/services_account.py:287-323`) and from `adjust()` (`:286-292`).
  - Welcome-bonus count without a lock: `:72-83,108-113`.
- Impact: on MySQL/MariaDB two friends signing up with one referral code at the same moment deadlock (500, sign-up rolled back). This is the same InnoDB FK-lock mechanism that failed CI on 2026-11-26. In addition, simultaneous sign-ups on one phone can pass `WELCOME_BONUSES_PER_PHONE`.
- Recommendation: lock or update the wallet row before inserting the entry, as `hold_phone` now does. Add wallet cases to `grama/tests/test_concurrency_threads.py`.

**BE-SEC-201: Wallet sign-up and code endpoints are unthrottled: account enumeration and email sending to any address**
- Severity: Medium · Effort: S
- Evidence:
  - `apps/citizens/views_account.py:45-47,63-73` (AllowAny, no throttle);
  - `apps/citizens/services_account.py:126-138,232`: 409 `mobile_in_use` / `email_in_use` before any limit;
  - `apps/citizens/codes.py:101-119`: limits only per address, account and client-sent `android_id`;
  - `apps/citizens/templates/citizens/email/code_en.txt:2` ("Hello {{ name }}"), with the name up to 100 characters (`serializers_account.py:18`);
  - `grama/settings.py:484-507`: no default throttle.
- Impact:
  - Anyone can test, without limit, whether a number or email has an account. This undoes the decoys of BVTGC-152.
  - A script can send up to 5 code emails a day to every address on a list, with attacker-chosen text in the greeting. That is phishing from the platform's domain, burns SMTP quota and harms sender reputation.
  - Every sign-up forces an Argon2 hash.
- Recommendation: scoped DRF throttles per IP and globally on sign-up, resend, forgot, delete-code and wallet login, on the shared throttle cache. Run the limits before the in-use check. Leave the name out of the email or restrict its characters. Answering every sign-up the same way is an owner decision (contract section 21).

**BE-SEC-202: Referral and welcome-bonus points can be farmed**
- Severity: Medium (grows once points can be redeemed) · Effort: M
- Evidence:
  - `apps/wallet/services.py:94,105-113`: phone identity is the client-sent `signup_android_id_hash` (`serializers_account.py:27`).
  - The mobile number is never confirmed: `services_account.py:578-603`.
  - Email variants are folded for Gmail only: `services_account.py:89-96`.
  - "Active days" are met by `GET citizen/account/`: `services_account.py:467-473`.
  - `REFERRALS_PER_MONTH=30` applies per referrer only: `grama/settings.py:790`.
- Impact: points can be minted without limit with scripted accounts. Contained today only because the wallet is off (`settings.py:778`) and there is nothing to redeem.
- Recommendation: before points carry value, tie bonuses to an attested device (an integrity-checked citizen token), confirm the mobile number (BVTGC-118), add sign-up limits per IP, and watch for referrer outliers.

**BE-SEC-211: Email-code limits and the 5-try cap are check-then-act**
- Severity: Medium · Effort: S
- Evidence:
  - `apps/citizens/codes.py:101-119` then the INSERT at `:143`, with no lock.
  - `:190-204`: `attempts` is read once (`:197`), the hash is compared, and the success UPDATE (`:204`) does not require `attempts < MAX_ATTEMPTS`.
- Impact: a parallel burst of guesses is compared in full, so the attacker gets about the burst size in guesses instead of 5. Simultaneous requests can pass the resend cooldown and the daily send limits.
- Recommendation: increment `attempts` with a conditional UPDATE before comparing, and compare only when it succeeded. Lock the owner row, or count again after the insert, for the send limits.
