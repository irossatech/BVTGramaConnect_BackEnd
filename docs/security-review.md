# Security review before UAT

Date: 2026-10-22, updated for the login and permissions rebuild of 2026-10-21 (`docs/authorization.md`), on 2026-10-30 for the gap review of 2026-10-27 (gaps G1 to G16, listed under "Gap review" below), and on 2026-11-25 for the citizen wallet (BVTGC-106, reviewed in BVTGC-130). Scope: backend API, ported public website and console, deploy configuration. Checked by reading the code and the deploy templates, the automated test suite, and `manage.py check --deploy` with production settings.

## Results

| Area | Status | What was checked |
|---|---|---|
| Login lockout | Pass | django-axes: 5 failed logins for one username from one IP address lock that pair for 15 minutes. Since 2026-11-25 (WEB-SEC-019, lead's decision) a ceiling per username also applies: 20 failed logins for one username within an hour, from any addresses, lock that username from every address for 15 minutes after the last of them (`LOGIN_MAX_FAILURES_PER_USERNAME`, `LOGIN_USERNAME_WINDOW_MINUTES`). Tries during either lockout do not extend it, so a stranger can keep an official out for 15 minutes at a time at most; a successful login, an unlock or a password reset clears the count. Unknown usernames get the same answer as wrong passwords, and take as long. On top of these, the cap per address against password spraying is back since BVTGC-105 (see "Per-IP limits" below). |
| Unlock | Pass | An admin ranked above the user, with `accounts.unlock_user` over their area, can unlock early; a password reset also clears the lock. Each lockout is audited once (`auth.locked_out`), each unlock as `user.unlocked`. |
| Passwords | Pass | Argon2 hashing; older PBKDF2 hashes are upgraded at the next login. Django's validators apply to every new password: at least 12 characters for every official (since 2026-11-19; G12 had 12 for admins and 8 for Panchayat members), not common, not all digits, not like the username, name or email, and at least one capital letter, one small letter, one number and one special character. Generated temporary passwords meet the same rules. A temporary password is typed by the admin or generated, shown once in the API response, and never stored readable, emailed, logged or audited. There are no default passwords per role. |
| Forced password change | Pass | New and reset accounts must choose their own password first. Until they do, every endpoint except `GET /me`, password change, the logouts and refresh answers 403 `password_change_required`, for tokens and console sessions alike. |
| Session revocation | Pass | Blocking, a password change, an admin reset and "log out everywhere" bump the user's token version and blacklist every open refresh token in one transaction. The next request with an old token or console session gets 401 `session_revoked`. Unblocking does not revive old tokens. |
| Console session and CSRF | Pass | The console uses a Django session, not tokens. The `sessionid` cookie is HttpOnly, SameSite=Lax and Secure on the server. Every write needs the `X-CSRFToken` header, and the session ends after 30 idle minutes. `CSRF_TRUSTED_ORIGINS` is written by `deploy/setup.sh` from the server's domains. |
| Console access | Pass | Only holders of `web_admin.access_web_console`, today the Super Admin group, get a console session; others get 403 `not_console_user`. The permission is checked again on every request, so a session stops working as soon as the permission is lost. |
| Area permissions | Pass | Roles are Django groups and actions are Django permissions, limited to each role assignment's area. The matrix tests cover every group × every permission × the same area, the parent, a sibling and another district. User actions also need a group ranked strictly below the actor's. |
| Row-level security and triggers | Not used, by design | Area isolation is enforced in the application, inside the SQL of every query: lists filter with `authz.area_q`, `authz.manageable_users` and `apps.posts.services.visible_posts`, and objects outside reach answer 404. Database row-level security is not used: MySQL and MariaDB have none, the server database is not chosen yet, the portable-ORM rule rules out vendor-specific policies, and the app reaches the database as one user, so the database cannot tell officials apart. Audit entries are not written by triggers either: `apps.audit.services.record` writes them in the same transaction as the change, so a failed change leaves no entry and a change never goes unaudited. What remains is direct database access, which bypasses both; the database must accept connections only from the server itself, with its own user and password per environment and no shared or default credentials. |
| Per-IP limits | Pass, with one open item | Removed on 2026-11-20 and put back before going live (BVTGC-105): the cap per address on failed logins (any usernames, from one IP within an hour; **off by default** (`LOGIN_IP_MAX_FAILURES=0`) until production confirms real visitor addresses, BVTGC-39, since a hidden address or a mobile network's shared one would block everyone; `LOGIN_IP_WINDOW_MINUTES`; audited once as `auth.ip_locked_out`, never with the IP; tries while blocked are not counted, and a success or an unlock does not clear it) and the Nginx template's request limits (`gc_login`: 10 a minute on the login and password-change paths; `gc_api`: 20 a second, bursts of 60, on the rest of the API, the feed and the shared links). The contact form has **no per-IP limit by the lead's final decision** (2026-11-25); its hidden honeypot field stays, and the console lists every message, so spam is visible at once. **Open:** the login throttle of gap G1 (30 logins an hour per IP) is not back; whether it should be is not decided (many officials can share one office network). The fail2ban jail for addresses hitting the Nginx limits is not back either (fail2ban still guards SSH). |
| Caller's IP address (`X-Real-IP`, backend audit BE-SEC-101) | Pass with a note | Put back before going live (BVTGC-105; first merged as `6c2bcc4`, reverted on 2026-11-20 by `8c351fd`). Every per-address limit (the lockout per username and IP, the cap per address) counts the address from `grama.http.client_ip`. It believes `X-Real-IP` only when `TRUST_X_REAL_IP` is on, the connection came from the server's own network (the same machine, a unix socket or a private address) and the header holds one valid IP; a caller connecting from a public internet address (on qa, the open port) is counted by that address whatever header it sends, so changing the header on every try does not get round the limits. Tests: `grama/tests/test_client_ip.py`, `apps/accounts/tests/test_real_ip_spoof.py`. **Note:** the server's Nginx must set the header itself (`proxy_set_header X-Real-IP $remote_addr;`, as `deploy/templates/nginx-proxy.conf` does), not pass on the caller's. |
| Uploads | Pass | Photos: only JPEG, PNG and WebP; size limit; decompression-bomb guard; metadata stripped by re-encoding to WebP. Videos (owner decision Q8): MP4 or MOV only, checked by extension and by the file's own header; at most 60 MB and 60 seconds (lead's decision of 2026-11-14; measured on the server with ffprobe; banner videos any length, 60 MB). Up to 3 photos or one video per post, never both, for officials, the Super Admin and citizens alike (lead's decision of 2026-11-13; `MAX_PHOTOS_PER_POST` 3); each request has a time budget for checking its files (`MEDIA_PROCESSING_BUDGET_S`, 90 s). The poster is re-encoded to WebP like a photo. The video file is stored without its metadata (G7, owner decision of 2026-11-03): ffmpeg copies the video and audio streams without re-encoding, drops the GPS place, phone, dates, chapters and data streams, and moves the index to the front; a file it cannot copy is refused (415). Banner ad videos and citizen videos go through the same step. Without ffmpeg (a laptop) the file is kept as sent; the server installs it. Nginx caps request bodies at 60 MB (70 MB on the three upload addresses, for one 60 MB video) and serves /media/ with a sandboxing Content-Security-Policy and nosniff. |
| Personal data in logs | Pass | No password, temporary password or token is written to logs, audit entries or background-job arguments. A failed push is audited with the topic or user id, the number of tries and the error type only. Nginx logs URLs without query strings, so searches by email or mobile number are not recorded. Gunicorn keeps no access log of its own (G3), so it cannot undo that. The audit export's entry keeps only the filter names and values that hold no personal data; a search text is noted as "(given)" (G14). |
| Password change guessing | Pass | A wrong current password answers `invalid_credentials` and is audited. The 5th within 15 minutes (`PASSWORD_CHANGE_MAX_FAILURES`, `PASSWORD_CHANGE_WINDOW_MINUTES`) ends every session of the user, so a stolen session cannot be used to guess the password: the next try needs a real login, where the lockout applies (G9). |
| API documentation | Pass | `/api/schema/` and `/api/docs/` answer only console users in production (`API_DOCS_PUBLIC` off): the schema maps every endpoint, the admin ones too. Laptops and the qa server keep them open for the client teams (G4). |
| CSV exports | Pass | The audit export and the reports write text cells starting with `=`, `+`, `-`, `@`, a tab or a carriage return with a leading apostrophe (`grama/csvsafe.py`), so a post title or a name never runs as a formula in Excel. Numbers stay numbers (G15). |
| Audit "via" label | Pass | "console" or "app" comes only from the authenticator that accepted the request; client headers are ignored (G13). |
| Secret key | Pass | Production refuses to start with the `.env.example` value, the development key, a `django-insecure-` key or anything Django calls weak (under 50 characters or under 5 different ones). `setup.sh` generates a random one. Citizen phones are recognised across reinstalls by hashes keyed with `PHONE_HASH_KEY` (empty means `SECRET_KEY`, as before), so a rotation that first copies the old key there (`deploy/RUNBOOK.md`, Rotating secrets) keeps their daily limits and blocks (BE-SEC-109, BVTGC-111). |
| Personal data in URLs | Pass with a note | No endpoint puts a password or token in the URL. The users and audit searches take a q parameter that can contain an email or mobile number; it stays out of Nginx logs, but browsers keep it in their history on the Super Admin's own machine. |
| Public data | Pass | The citizen feed, the upcoming and urgent lists and the website showcase show posts, areas and the publishing role only: no names, mobile numbers or emails of officials. |
| Important numbers | Pass with a note | Public by design: one village at a time, no bulk export. Writes need `contacts.manage_contact` over the number's area, lists filter in SQL, and numbers outside reach answer 404. A strict phone grammar keeps USSD codes such as `*#06#` out of the app's dialler. A 10-digit mobile is published only with the consent tick, and audit entries mask every phone (`******0001`). Removal hides a number at once; the row stays only for the audit trail. Note: an official's own mobile is personal data under the DPDP Act 2023, so office, landline or CUG numbers are preferred (decision C2). |
| Contact messages | Pass | Only holders of `web_public.manage_contact_messages`, the Super Admins, can list them or mark them handled (owner decision Q16); everyone else gets 403. Marking one handled is audited with the message number only, never the sender's name or mobile number. |
| Django admin | Pass | Off on every server since 2026-11-11 (lead's decision): with `DEBUG=False`, `DJANGO_ADMIN_ENABLED` defaults to off and `/django-admin/` answers 404. Officials, roles and settings are managed in the console; anything else goes through `manage.py shell`. It is on only on laptops (`DEBUG` on), or on a server whose `.env` says `DJANGO_ADMIN_ENABLED=True`; on servers built with `setup.sh` Nginx still answers `/django-admin/` with 404 itself (BE-OPS-205), so it stays closed there. When on, logins there go through the same lockout. Only Super Admins can see or edit groups and role assignments, and group permission changes are audited. |
| Push devices | Pass | `POST /devices/` without a login never unlinks a device already linked to an official, so a known push token cannot cut an official off their review alerts; only the official's logout (`DELETE`) or another official's login on the phone does (G8). qa sends to `qa_` topics only (`FCM_TOPIC_PREFIX`), so test posts never reach real phones. |
| Dependencies | Pass | Every package is pinned in `requirements.txt`. `deploy.sh` runs `pip-audit` on it before migrating and stops on any known vulnerability; CI runs it on every pull request into `dev` and every Monday, and Dependabot opens a pull request when a pinned package has a fix (G10). |
| Code scanning | Pass | Bandit and Semgrep (`p/python`, `p/django`, `p/secrets`) run in CI (`.github/workflows/security.yml`) on every pull request into `dev` and fail it on any Medium or higher finding. The scan of 2026-10-31 found 0 High, 0 Medium and 10 Low (Bandit): eight false positives on names such as `tv` and `gc_tv` that look like passwords, and the ffprobe and ffmpeg calls, accepted because they take argument lists, no shell, timeouts and server-made paths. Limits: Semgrep sees git-tracked files only, the deploy scripts get no shell rules beyond `p/secrets`, and the web repo is not scanned here. |
| Old data | Pass | A daily job deletes expired refresh tokens, expired console sessions and failed background jobs older than 30 days. The audit log is never deleted. |
| Production settings | Pass | Production is `grama/settings.py` with `DEBUG=False`; every production `.env` must say so (`deploy/setup.sh` and `deploy/qa/BVT-deploy.sh` write it), because an unset `DEBUG` means development. It refuses to start without a strong SECRET_KEY, DATABASE_URL, MEDIA_ROOT and STATIC_ROOT; without ALLOWED_HOSTS it answers every request 400. Django sends `Strict-Transport-Security` for one year on what it answers, the API and Django admin (`SECURE_HSTS_SECONDS`, G11 as the gap review gives it); Nginx sends it on the website and console pages it serves itself, so no response carries two. Port 80 redirects to HTTPS in Nginx. The production settings silence only that redirect check (`security.W008`) and the HSTS subdomain and preload checks (`security.W005`, `security.W021`), which stay off until the owner's domain is known because they bind every subdomain to HTTPS for a year. `deploy.sh` runs the security checks with `--fail-level WARNING` before migrating: any other security warning stops the deploy (`STRICT_CHECKS=1`, now the default) (G11). |
| Post translation | Pass by design, off by default | While `TRANSLATION_PROVIDER` is off, nothing leaves the server. When on, only the title and body of **published** posts, text the public feed already shows, go to Google or Bhashini over HTTPS, from the background worker. Never names, phone numbers, device ids or unpublished text. The Google key goes in a header, not the URL. Provider errors and logs carry the status code and error type only, never the post's text. A citizen may write personal details into a post's body; once published, that text was public anyway. |
| Content-Security-Policy | Pass (template), with a note | Since 2026-11-12 (web audit WEB-SEC-001) the policy in `deploy/templates/nginx-security.conf` allows scripts only from our own origin, with no `'unsafe-eval'`: the website and console are a static Next.js build with no inline scripts and no eval. Inline styles stay allowed, because the markup keeps the prototype's inline styles. All scripts, styles and fonts are served from our own origin (fonts from `/fonts/` since 2026-11-04), so the policy names no other site and no page loads anything from Google. Since 2026-11-16 (web audit WEB-SEC-003/WEB-HDR-001) the policy allows no `data:` fonts or pictures (the build uses none: every website page and console screen was checked in Chrome under the new policy, with no violation), and the pages also send `Permissions-Policy` (camera, microphone, location, payment and USB off) and `Cross-Origin-Opener-Policy: same-origin`; Django sends COOP on the API itself. **Note:** production and the qa server run on the hosting panel's own Nginx, not this template, and on 2026-11-12 neither sent a Content-Security-Policy; the production team adds the same headers there (`deploy/RUNBOOK.md`, Security notes). |
| Private answers not stored | Pass | Since 2026-11-16 (web audit WEB-HDR-002) every API answer carries `Cache-Control: no-store, private` unless its view marks it public (`grama/cache_headers.py`), so a browser keeps no copy of personal data (users, mobiles, contact messages, service requests, audit log, CSV exports) on a shared computer after logout. The public feed, banners, important numbers, geography, services and bills keep their public caching. Tests: `grama/tests/test_cache_headers.py`. |
| Citizen accounts kept apart (wallet, BVTGC-121, BVTGC-130) | Pass | A citizen's wallet account holds only the `CITIZEN` group and `wallet.use_wallet`. The officials' login and the console refuse it like a wrong password. `grama/tests/test_citizen_token_scope.py` walks every route of the API: with a citizen's token, each of the officials' and the Super Admin's 104 route-and-method pairs answers 403 `permission_denied` before looking anything up, and a new route fails the test until it refuses citizens or is listed as public or citizen-facing. The permission matrix (`apps/accounts/tests/test_matrix.py`) calls every wallet permission's endpoint for every group, the Citizen group included. |
| Citizen passwords (D15) | Pass with a note | 8 characters of any kind, shorter than the officials' 12 with complexity, by the Admin's decision of 2026-11-25. What makes up for it: the common-password list and the checks against the name, email and number; the same lockouts as officials (5 per account and address, 20 per account an hour from anywhere, and the cap per address when a server switches it on); a reset only with a code sent to the account's confirmed email; Argon2 hashing; and the points have no cash value until Bills & Recharges, before which every paying citizen confirms the number (D17). **Note:** the Nginx login limit (`gc_login`, 10 a minute) covers the officials' login paths only; the citizen paths get the general API limit (open item 9). |
| Email codes (sign-up, forgotten password, website deletion) | Pass | 6 digits, 10 minutes, 5 tries, then dead; stored only as an HMAC with the row's id; 60 seconds between codes; at most 5 a day per account or address and 10 per phone. A forgotten password and the website's deletion give the same answer for an unknown, blocked or deleted login, and a deletion needs a `DELETE` code (a reset code does not work there). Sign-up does say when a number or email is registered (FR-11, so the citizen can log in instead): that tells a caller an account exists, accepted by the requirements. |
| SMTP secret (BVTGC-122) | Pass with a note | Email now goes out (codes and account notices for citizens only; officials still get none). `EMAIL_HOST_PASSWORD` lives only in the server's `.env`, never in git; TLS is on (`EMAIL_USE_TLS`). A failed send is logged with the error type only, never the address or the code. This reverses "SMTP credentials: nothing is emailed" of the gap review below. Rotate it like the other secrets (`deploy/RUNBOOK.md`). |
| Wallet personal data | Pass with a note | New: the name, the email in full (codes go there; the console sees it masked), the mobile number as a keyed hash plus the last 4 digits, the password hash, the village, the 18+ and consent dates, and app-use days (kept 60 days). Deletion (app, website with a code, or the Super Admin) removes the name, email and number at once; a fingerprint of the number and email stops a second welcome bonus for `CITIZEN_DELETED_KEEP_DAYS` (365, subject to legal review, Q9), then housekeeping clears it. `apps/citizens/tests/test_wallet_privacy.py` walks the whole wallet and finds no email, number, password, code or token in any log record, audit entry or background job. **Note:** earlier audit entries keep the citizen's name; the audit log cannot be changed (open item 10). |
| Wallet fraud controls | Pass with a note | Points are held 7 days and confirmed only if the new citizen used the app on 2 of them; at most 30 confirmed referrals a month per referrer; no referrer reward between accounts that signed up on one phone; at most 3 welcome bonuses per phone, deleted accounts counted; none again for a deleted account's number or email. The Super Admin reviews and rejects referrals, corrects balances (never below zero, one conditional UPDATE) and blocks accounts, each audited; a daily check compares every balance with its history (`wallet.mismatch`). Each decision is one conditional UPDATE, so the first one wins, and idempotency keys stop double payments. **Note:** the phone rules trust the `android_id` the app sends; a determined fraudster can vary it, so the hold, the active days, the monthly cap and the Super Admin's review carry the weight until the number is confirmed (D17). |
| Super Admin help after a call-back (D16) | Pass with a note | Setting a new email or releasing a number needs `called_back: true` and a reason; both are audited, codes already sent stop working, and the old address gets the "email changed" notice. The server cannot know the call really happened: the Super Admin follows the call-back procedure. |
| Wallet switch | Pass | While `wallet_enabled` is off, every citizen wallet endpoint answers 404; a test walks all of them (`apps/wallet/tests/test_wallet_settings.py`). The Super Admin's tools stay on, so help, exports and deletions still work. |

## Open items

1. **Django admin: office IPs. Closed 2026-11-11.** Django admin is off on every server instead (see Django admin above), so no office IP list is needed.
2. **Not tested on a real server.** The deploy scripts pass syntax and shellcheck checks, but Nginx, certificates, firewall and backups have not run on Ubuntu yet. The console's Secure session and CSRF cookies are first exercised over real HTTPS there.
3. **Video metadata (G7): closed 2026-11-03.** The owner chose to strip it; see Uploads above. On the server, check once that `ffmpeg` and `ffprobe` are installed (`deploy/setup.sh` installs them), or videos keep their metadata there.
4. **Second factor for Super Admins (G5, owner decision).** Console login is username and password only. TOTP for console users, or the risk accepted in writing.
5. **Admin password length (G12): closed 2026-11-03.** The owner chose 12 for admins, 8 for Panchayat members. A shorter existing admin password must be changed at the next login. **Raised on 2026-11-19: 12 for every official**, Panchayat members included; a member's shorter password must be changed at the next login the same way.
6. **Untracked files with tokens and test passwords (G16).** The review found `test_execution_results.json` (15 JWTs), test scripts with the `super.admin` and village passwords, an API specification `.docx` and screenshots in a repo copy. They are not in git and not in this checkout, and `.gitignore` now lists them, so a `git add .` cannot commit them. Whoever holds them deletes them; the `.docx` is not shared until its screenshots are checked.
7. **Make the scans required (G10).** `.github/workflows/security.yml` runs on every pull request into `dev`, but GitHub lets a red pull request merge until the repository's branch protection for `dev` lists the three scan jobs as required checks. A repository admin sets that once.
8. **Per-IP limits and `X-Real-IP`: closed 2026-11-25 (BVTGC-105)**, except the login throttle. The BE-SEC-101 fix, the cap per address and the Nginx limits are back; the cap per address ships off (`LOGIN_IP_MAX_FAILURES=0`) until production confirms real visitor addresses (BVTGC-39), then a server may switch it on, starting high; the contact form stays without a per-IP limit (lead's final decision). Still open: whether the login throttle of 30 logins an hour per IP comes back (not decided).
9. **Citizen login and code addresses have no per-address limit of their own (wallet, lead's decision).** The citizen login shares the officials' lockouts, and codes are capped per account, address and phone, but one internet address can still ask for codes for many different email addresses (each capped at 5 a day), which costs sending reputation, and the `android_id` cap is the app's word. Suggested: put `citizen/auth/` under the Nginx `gc_login` limit (10 a minute per address), and a server cap of about 30 codes an hour per address. Not done without the lead's decision.
10. **A deleted citizen's name stays in earlier audit entries (wallet, owner's decision).** Deletion removes the name, email and number from the account, but entries written before (logins, changes) keep the name as the actor or label; masked emails and last 4 digits were never full data. The audit log refuses changes by design (`AuditLog.save`). Whether the DPDP erasure duty needs those names replaced is for legal review; until then they stay.
