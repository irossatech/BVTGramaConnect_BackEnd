## 1. Executive summary

**Health score: 6 / 10. Risk level: Medium.** The risk becomes High if the production panel's nginx does not overwrite `X-Real-IP`; that is not verified.

The codebase is well structured and much better than average on authorization:
- permission and area are checked separately, and lists are filtered in SQL
- no IDOR was found in any view
- no raw SQL
- a race-safe post state machine
- a large test suite built on permission matrices

The risks sit at the edges: how the servers are actually deployed, personal data that leaks into permanent records, citizen anonymity being abused, and weak operational visibility.

**Top 5 risks**
1. **The login lockout can be bypassed on qa, and maybe on production (BE-SEC-101, High).**
   - `TRUST_X_REAL_IP` defaults to True whenever `DEBUG=False`.
   - The qa server runs Django directly on `0.0.0.0:<port>`.
   - Any client can send its own `X-Real-IP` header and make every login attempt look like a new address. That defeats the axes lockout, the IP-wide cap and the login throttle, which leaves unlimited password guessing.
   - Production is safe only if the panel's nginx overwrites the header. That is not verified.
2. **Full email addresses and mobile numbers are in the permanent audit log (BE-SEC-001, High).**
   - This breaks a project non-negotiable.
   - The audit table refuses deletes, and the data is exported to CSV.
   - Typed usernames (BE-SEC-007) and free text (BE-SEC-107) add to it.
3. **Citizen identity relies on a client-supplied `android_id` (BE-SEC-002, High).**
   - This allows reading another phone's service requests (name, phone, email, address) and evading blocks.
   - Play Integrity is off on production and registrations per IP are unlimited, so nothing else limits it.
   - Unbounded citizen media adds to the exposure (BE-PERF-003).
4. **The production setup is outside the repo, and its backups are weak (BE-SEC-003, BE-SEC-004).**
   - The panel nginx is the only guard for `/django-admin/`, rate limits and body size, and its config is not in the repo.
   - Backups are unencrypted and kept on the same host.
5. **Failures are hard to see and some are wrongly handled (BE-OBS-101, BE-ERR-101 to 103, BE-REL-101).**
   - There is no error tracking and no request IDs, and job failures are invisible.
   - Several bad inputs and outages of outside services give a 500.
   - A retried push job can send duplicate high-priority pushes.

## 3. Architecture assessment

**Pattern.** A modular Django monolith. There are 14 apps under `apps/` and the project package `grama/`. DRF is in front, with a service layer (`services.py`, `selectors.py`) in most apps. Domain signals carry cross-app side effects such as notifications and translation. Background jobs use django-q2 with the database as the broker.

**Strengths (with evidence)**
- **Single-writer rules are kept:**
  - Post status changes happen only through conditional UPDATEs in `apps/posts/services.py`, the main one at `:618`, with signals sent on commit at `:281`.
  - Areas are written only by `apps/geography/services.py`, contacts only by `apps/contacts/services.py`, service requests only by `apps/service_requests/services.py`.
- **"posts never imports notifications" holds:** there are 0 import edges from posts to notifications. Notifications reacts through `apps/posts/signals.py`.
- **Permission logic is central:** `apps/accounts/authz.py` and `permissions.py`. Group names appear outside `role_matrix.py` only in the seed commands, never in views.
- **Signals are few:** 11 handlers, each with a `dispatch_uid`, documented, and wrapped in `_safely` where they reach outside (`apps/notifications/receivers.py:18-22`).
- **Serializers are thin:** no `validate`, `create` or `update` method is 20 lines or longer.

**Weaknesses:** see BE-ARC-101, BE-ARC-102 and BE-QUA-102 in section 4. In short:
- `accounts` has no service layer. `apps/accounts/views_users.py`, 465 lines, holds `UserViewSet` (241 lines), which mixes writes, peer rules and audit.
- Some views write and audit outside a transaction.
- `web_admin/api.py:29-40` queries other apps' models directly, about 20 querysets. That is acceptable for platform-wide reports, but the dashboard re-implements `runtime()` and got it wrong (BE-COR-101).
- Layering is inverted in places:
  - `web_public/api.py:27` imports from `feed.views`
  - `grama/logos.py:34` imports `apps.posts.media`
  - `posts/views.py:23` imports `apps.citizens` at module level, closing a posts↔citizens cycle that works only because of load order.

**BE-ARC-101: Audit entries written outside the change's transaction**
- **Severity:** Medium
- **Evidence:**
  - `apps/posts/views.py:472-476`: runtime settings, `SettingOverride.update_or_create` then `record()`.
  - `apps/posts/views.py:108-117`: categories.
  - `apps/notifications/views.py:167-168`: templates.
  - `ATOMIC_REQUESTS` is not set (`grama/settings.py:64-93`).
- **Impact:** a failure between the write and the audit leaves a change with no audit entry. That breaks the rule "write audit entries inside the transaction of the change".
- **Recommendation:** wrap each write and its audit in one atomic block, or move these writes into service functions that do.
- **Effort:** S

**BE-ARC-102: `accounts` has no service layer**
- **Severity:** Low
- **Evidence:**
  - `apps/accounts/views_users.py:259-284, 394, 439, 459` create, save and delete `User` and `RoleAssignment` directly in views.
  - `views_auth.py:208-214` changes passwords in the view.
- **Impact:** user-management rules can't be reused by commands or Django admin, which is why the admin skips them (BE-SEC-008). BE-SEC-001 also slipped in here.
- **Recommendation:** extract user create, update, block, reset and role changes into `apps/accounts/services.py`, with audit and revocation, and call it from the API and the admin.
- **Effort:** M

**BE-QUA-101: Duplicated logic across apps**
- **Severity:** Low
- **Evidence:**
  - Image to WebP: `grama/logos.py:35-58`, `apps/ads/services.py:55-82`, `apps/posts/media.py:68-98`.

- **Impact:** a security fix to the decompression-bomb guard has to be made three times, and the rules drift apart.
- **Recommendation:** one shared image helper, one phone validator module, and shared ordering and key helpers.
- **Effort:** M

**BE-QUA-102: Import cycles and inverted layering**
- **Severity:** Low
- **Evidence:** `apps/posts/views.py:23` (top-level import of citizens, while `citizens/services.py:38-39` imports posts); `apps/web_public/api.py:27` (a view module imports another view module); `grama/logos.py:34`.

## 5. Error handling findings

The custom handler `grama/exceptions.py:85-118` produces `{"error": {...}}`. `handler404` and `handler500` are wired (`grama/urls.py:23-24`) and return the JSON shape for `/api/` with no details (`grama/views.py:37-46`). **No stack traces or SQL reach clients with DEBUG off.** The handler maps DRF exceptions, `Http404` and `PermissionDenied`; anything else becomes a generic 500.

**BE-ERR-101: Bad input gives a 500 instead of 400 or 404 (extends BE-COR-001)**
- **Severity:** Medium
- **Evidence:**
  - **Non-UUID ids:** `apps/posts/views.py:180` (no `lookup_value_regex`; `/posts/abc/`); `:348-351` (regex `[0-9a-f-]+`); `:193` (`?author=`); `apps/audit/views.py:86` (`?actor=`); the `users/` router.
  - **Impossible dates:** `audit/views.py:68` (`parse_date("2026-02-30")` raises `ValueError`).
  - **`isdigit()` then `int()` on public endpoints** (`"²".isdigit()` is True, `int("²")` raises): `apps/feed/views.py:75-81`, `apps/contacts/views_public.py:34-37`, `apps/ads/views.py:32-35`, `apps/geography/views.py:54-56`; also `posts/views.py:166-168, 407-409`, `views_users.py:168-174`, `web_admin/api.py:77`.
  - **Contact types:** `contacts/views_admin.py:194` (non-integer id).
  - **CSV imports:** `geography/importer.py:266-270` (a NaN latitude raises `InvalidOperation` outside the `try`); `importer.py:157` and `contacts/services.py:447` (`csv.Error` on a field over 131,072 characters).
  - **Ads:** `ads/serializers.py:34` (a JSON list body).
- **Impact:** anonymous callers can produce 500s, which fill logs and break the contract's error codes. Contacts already shows the fix (`contacts/views_admin.py:64`, tested at `contacts/tests/test_admin.py:175`).
- **Recommendation:** add `lookup_value_regex` to the posts and users routers; parse ids and dates with explicit validation; map Django `ValidationError`, `ValueError` from parsing, and `csv.Error` to 400 `validation_error`.
- **Effort:** S

**BE-ERR-102: ffprobe and ffmpeg timeouts are not caught**
- **Severity:** Medium
- **Evidence:** `apps/posts/media.py:182-188` (30 s), `:200-205` (60 s), `:224-230` (120 s). `subprocess.TimeoutExpired` is not handled. They run inside the upload request.
- **Impact:** one slow or crafted video holds a worker for up to 210 s and ends in a 500, or a 504 from nginx at 60 s.
- **Recommendation:** catch the timeout and answer 415 or 422, and move video processing to the job worker (see BE-PERF-003).
- **Effort:** S

**BE-ERR-103: A Play Integrity outage gives a 500 on citizen registration**
- **Severity:** Medium
- **Evidence:**
  - `apps/citizens/services.py:168-179` catches only `IntegrityFailed`.
  - `apps/citizens/integrity.py:84-93` can raise network, Google auth, missing-file or JSON errors.
  - It reloads the credentials file and fetches a new OAuth token on every call (`:84-88`).
- **Impact:** once integrity is turned on (required before the app goes to Google Play), a Google hiccup blocks every new citizen with a 500, and each registration pays for an OAuth round trip.
- **Recommendation:** wrap all verifier failures in a clear 503 code, and cache the credentials and session per process.
- **Effort:** S

**BE-REL-101: A topic push job can time out and be re-run, sending duplicate pushes**
- **Severity:** Medium
- **Evidence:**
  - `apps/notifications/services.py:156-164` puts every target topic in one job; `POST_MAX_TARGETS` is 200 (`grama/settings.py:412`).
  - `apps/notifications/tasks.py:44-46` sends them one by one with retries that sleep (`grama/retry.py:47-48`).
  - `Q_CLUSTER` has `timeout` 120 and `max_attempts` 3 (`settings.py:388-390`).
- **Impact:** when FCM is slow, a job is killed partway and re-run, and citizens get the same high-priority push again.
- **Recommendation:** one job per topic, or record which topics were sent, and retry through scheduling instead of sleeping.
- **Effort:** S

**BE-COR-101: The dashboard reads the escalation setting under the wrong key**
- **Severity:** Medium
- **Evidence:**
  - `apps/web_admin/api.py:68` filters `SettingOverride.key="review_escalation_hours"`.
  - The writer stores `"REVIEW_ESCALATION_HOURS"` (`apps/posts/views.py:463, 473`), and `runtime()` reads it that way (`posts/services.py:101`).
  - Re-checked with `grep`.
- **Impact:**
  - After a Super Admin changes the setting, the dashboard and the review-time report (`api.py:185, 262`) still show the environment default.
  - It behaves differently by database: MySQL's case-insensitive `utf8mb4_unicode_ci` collation would match the key, while SQLite and PostgreSQL would not. Tests on SQLite and the server could disagree.
- **Recommendation:** call `apps.posts.services.runtime("REVIEW_ESCALATION_HOURS")`, and add a test that changes the setting and checks the dashboard.
- **Effort:** S

**BE-COR-002: Count-then-insert limits and exists-then-save uniqueness (carried from BE_01, confirmed)**
- **Severity:** Medium
- **Evidence:** `citizens/services.py:258-264`, `service_requests/services.py:205-212`, `web_public/api.py:119-131`, `views_users.py:255-273`, `bills/services.py:32-37`. `contacts/models.py` has no unique constraint on type, phone and area.
- **Impact:** limits can be exceeded under concurrency, and some duplicates return 500 instead of 409.
- **Recommendation:** back uniqueness with constraints and map `IntegrityError` to 409. Accept or harden the soft limits.
- **Effort:** M

**BE-COR-003: Deleting a draft leaves its video file on disk (carried)**
- **Severity:** Low
- **Evidence:** `apps/posts/services.py:558-561`.
- **Impact:** orphaned files of up to 50 MB each.
- **Recommendation:** delete every file field, and add an orphan sweep.
- **Effort:** S

**Done well**
- Every outside HTTP call has a timeout: FCM 10 s (`push.py:156`), Play Integrity 10 s (`integrity.py:89`), translation 20 s, transliteration 4 s.
- Push retries stop at once on permanent errors, and dead tokens are removed (`notifications/tasks.py:60-61, 79-80`).
- Translation retries use one-off schedules (`posts/tasks.py:49-66`).
- `IntegrityError` becomes 409 in geography, user role changes and citizen registration.
- Non-UTF-8 CSV uploads get a clean 400.

## 6. Security findings

### 6.1 Object- and function-level authorization (OWASP API1, API5)

**I found no IDOR.** Probes that came back clean:
- **Role assignments:** looked up with `pk` and `user`, the user coming from `manageable_users` (`apps/accounts/views_users.py:373-378`).
- **Post media delete:** `get_object_or_404(PostMedia, pk=media_id, post=post)` on a scoped post (`posts/views.py:350-351`).
- **Every post detail and action:** scoped by `visible_posts`, answering 404 (`posts/views.py:176-180`, `services.py:187-190`). Services re-check the author or reviewer (`services.py:501, 586-603`, `media.py:119-123, 375`).
- **Notifications:** `get_object_or_404(..., user=request.user)` (`notifications/views.py:120`).
- **Service requests:** `visible_requests` (`service_requests/views.py:146-148`).
- **Contacts:** answer 404 out of reach (`contacts/views_admin.py:112-117`).
- **Feed, share and posts by id:** published only, with ids parsed as UUIDs, at most 50 (`feed/views.py:59, 172-184`; `share/views.py:100`).
- **Citizen posts:** filtered to the calling device (`citizens/views.py:78-84`).
- **Platform-wide admin endpoints:** all `HasPerm(..., PLATFORM)`.

**BE-SEC-102: A multi-area post is decided by a reviewer of any one of its areas, and admins auto-publish to any area**
- **Severity:** Medium (design; needs an owner decision)
- **Evidence:**
  - `apps/posts/services.py:161-166`: `reviewer_assignment` takes the best grant over any target. It is used by `review()` at `:586`, `set_urgent` at `:685` and `allowed_actions`.
  - `create_post` auto-publishes whenever the poster's assignment holds `publish_post` (`:344`, `:425-453`), whatever the targets.
  - `docs/authorization.md:260` records the 2026-10-28 decision "anyone who may post may post anywhere". `.claude/project.md` (Posts; "Visibility" decision) still says admin posts publish "only inside the admin's own area" and that only the Super Admin posts to the state.
- **Impact:**
  - A Village Admin can publish an urgent post to Everyone or to 200 areas at once, with a statewide high-priority push and no higher review.
  - A Panchayat member can add far-away areas to a post, and their own Village Admin alone publishes it everywhere.
- **Recommendation:** have the owner confirm which rule stands, then either require review from a reviewer covering every target (or the widest one), or limit auto-publish to targets inside the poster's area. Bring `project.md` into line in all three repos.
- **Effort:** M

**BE-SEC-008: Django admin skips the audit log and session revocation (carried, confirmed)**
- **Severity:** Medium
- **Evidence:**
  - `apps/accounts/admin.py:68-95`: `UserAdmin` has no `save_model`. It edits the password, `is_active`, `is_superuser` and `must_change_password` with no audit and no `token_version` bump.
  - `:105-108`: `RoleAssignmentAdmin.save_model` does not audit.
- **Impact:** a password set in the admin leaves existing refresh tokens valid for up to 30 days. Changes leave no trace.
- **Recommendation:** route the admin saves through account services with audit and revocation (BE-ARC-102), or make those fields read-only.
- **Effort:** M

**BE-SEC-016: Object permission answers 403, not 404 (carried; latent)**
- **Severity:** Info
- **Evidence:** `apps/accounts/permissions.py:54-57`. No current endpoint reaches it: every scoped detail view overrides `get_object` with its own 404.
- **Recommendation:** align it with the convention before a generic view starts using it.
- **Effort:** S

### 6.2 Mass assignment (OWASP API3)

**No mass-assignment issue found.**
- `MeUpdateSerializer` accepts only name, Telugu name and language (`accounts/serializers.py:258-261`; tested in `test_me.py:95`).
- `UserUpdateSerializer` excludes `is_active`, staff, `token_version` and `must_change_password`.
- Post status, author, decider and targets are set only in services through explicit inputs.
- Citizen block fields are written only by `citizens/services.py:332`.
- The only `fields="__all__"` is a Django admin form (`accounts/admin.py:57`).

### 6.3 Input validation and injection

- **SQL injection:** none. There is no `raw(`, `extra(`, `RawSQL` or `cursor.execute` in `apps/` or `grama/`. There is no `order_by` taken from request input, and `page_size` is capped at 100 (`grama/pagination.py:8-9`).
- **Validation done well:** lat/lng are bounded; enums are checked; text fields have `max_length`; ad links are limited to http and https (`ads/serializers.py:40-45`).
- Gaps are BE-ERR-101 above, and BE-SEC-105 and BE-SEC-104 below.

**BE-SEC-105: Notification template checks are incomplete**
- **Severity:** Low (Super Admin only)
- **Evidence:**
  - `apps/notifications/serializers.py:84` checks only variable names. `"{}"` passes, then `format_map` raises for every push of that kind (`notifications/services.py:56`).
  - `"{title:>999999999}"` passes and builds a string of about 1 GB at send time.
  - An unbalanced `"{title"` raises inside `validate()`, which gives a 500.
- **Impact:** a mistyped template breaks a whole kind of notification, or exhausts a worker's memory.

**BE-SEC-101: A spoofable `X-Real-IP` defeats lockout and throttling on qa, and possibly on production (new)**
- **Severity:** High
- **Evidence:**
  - `grama/settings.py:128`: `TRUST_X_REAL_IP` defaults to **True** whenever `DEBUG=False`.
  - `grama/http.py:6-9` returns the header as given, with no check of the proxy.
  - The qa `.env` written by `deploy/qa/BVT-deploy.sh:164-182` does not set `TRUST_X_REAL_IP`, so it is True.
  - qa runs `manage.py runserver 0.0.0.0:$PORT` (`deploy/qa/BVT-start.sh:95`), reachable directly with no proxy that would overwrite the header.
  - Every limiter keys on this value: axes (`lockout.py:51-53`), the IP-wide cap (`:89-104`), `LoginThrottle` (`views_auth.py:68-69`), the contact-message limit (`web_public/api.py:119`) and citizen registrations (`citizens/views.py:55`).
  - Production (`BVT-deploy.sh:225-226`) depends on the panel's nginx **overwriting** the header. Its config is not in the repo (BE-SEC-003).
  - The opposite misconfiguration also hurts: with trust off behind a proxy, every client shares the proxy's IP, so 50 failures an hour from anyone block all logins.
- **Impact:** on qa, an attacker sends a different `X-Real-IP` on each try and gets unlimited online password guessing against any username. qa holds real UAT officials and Super Admins. The same applies to production if the panel nginx passes a client-supplied header.
- **Recommendation:**
  - Default trust to off, and turn it on only where a proxy is known to set the header.
  - Better, trust the header only when `REMOTE_ADDR` is a configured proxy address.
  - Turn trust off on qa now, or put qa behind the panel proxy and close the direct port.
  - Confirm the production panel's `proxy_set_header X-Real-IP $remote_addr`.
- **Effort:** S

**BE-SEC-104: The trusted client-IP value is not validated as an IP address (new)**
- **Severity:** Low
- **Evidence:** `grama/http.py:7-9` returns any string. It is stored in `ContactMessage.ip_address`, a `GenericIPAddressField` (`apps/web_public/models.py:19`, written at `web_public/api.py:143`), and in axes' `AccessAttempt` and `AccessFailureLog`.

- **Recommendation:** validate with `ipaddress.ip_address` and fall back to `REMOTE_ADDR`.
- **Effort:** S

**BE-SEC-006: No application-level throttling on anonymous endpoints (carried, confirmed)**
- **Severity:** Medium
- **Evidence:**

- **Impact:** token minting, scraping, and costly unindexed searches. Only nginx limits on the root-server path apply, and those are unknown on production.

- **Impact:**
  - A change merged or pushed directly into `qa` or `main` (hotfixes, promotions with conflict fixes) is never scanned.
  - The weekly cron scans the default branch only.
  - "The whole suite stays green" is not enforced.
- **Recommendation:** add pytest and the migration check; run all jobs on pull requests into `qa` and `main`; make them required; pin actions by SHA; protect `qa` and `main`.
- **Effort:** S

**Supply chain:**
- Every package is pinned exactly in one `requirements.txt`, with no hashes (`--require-hashes` is not used).
- Dependabot ignores semver-major updates.
- Known vulnerabilities are **not verified**: pip-audit was not run locally.

## 11. Data protection (gaps to flag for legal review under India's DPDP Act, 2023; not legal advice)

**BE-DP-101: No retention, deletion or data-principal process for citizen and official personal data (new)**
- **Severity:** Medium
- **Evidence:**
  - Housekeeping removes only failed tasks, expired tokens, sessions and old login-failure IPs (`grama/housekeeping.py:27-49`).
  - Nothing ages out:
    - `ServiceRequest`: name, phone, email, address (`service_requests/models.py:98`)
    - `ContactMessage`: name, mobile, IP (`web_public/models.py:6-36`)
    - `CitizenDevice` with its FCM token (`citizens/models.py:16`)
    - `Notification` and `Device` rows
    - deactivated `User` rows with email and mobile
  - The audit log is immutable and holds personal data (BE-SEC-001, 007, 107).
  - A grep for consent, retention, erase or anonymise finds consent only for contacts' mobile numbers (`CONTACTS_REQUIRE_MOBILE_CONSENT`, `settings.py:463`).
  - No endpoint or command exists for access, correction or erasure requests.
- **Impact:** points for counsel, without legal conclusions:
  - storage limitation and erasure duties
  - notice and consent records for citizens who submit service requests and contact messages
  - handling of data-principal requests
  - personal data inside an audit trail that cannot be deleted
  - transfers to Google (Play Integrity, transliteration, FCM, optional translation)
  - breach readiness, which BE-OBS-101 weakens
- **Recommendation:**
  - Define a retention schedule per model with the owner and counsel, and implement it in housekeeping.
  - Add an erasure and anonymisation command for citizen records.
  - Keep personal data out of the audit log by design, or pseudonymise it.
  - Record the consent and notice version at citizen submission.
- **Effort:** M–L

**Done well:**
- The citizen token is stored only as a SHA-256 hash; IP and ANDROID_ID only as HMACs (`citizens/services.py:87-102`).
- Contacts mask phones in the audit log and require consent before publishing a mobile number.
- Video metadata, including GPS, is stripped (`posts/media.py:209-243`), and photos are re-encoded.
- Login-failure IPs are kept only for the window they are needed (`housekeeping.py:41-43`).
- The audit export does not record the search text (`audit/views.py:149-155`).

## 12. What is done well

- **Authorization:**
  - Permission and area are separate checks in one module (`authz.py`); lists are filtered in SQL; objects out of reach answer 404 in the views.
  - No IDOR was found across every view.
  - No group-name checks.
  - No mass assignment.
- **State machine:** conditional UPDATEs give "first decision wins" on any database; the audit entry and ReviewAction are in the same transaction; signals go out after commit.
- **Authentication:**
  - `token_version` revocation works for both JWTs and sessions.
  - Refresh tokens are blacklisted in bulk.
  - CSRF on the session login and logout.
  - Argon2 first.
  - Layered lockout.
  - Constant-time nonce checks.
  - The console requires its own permission.
- **No SQL injection surface:** no raw SQL anywhere, and no order-by taken from user input.
- **Uploads:** bomb-safe Pillow, re-encoding, server-side file names, ffmpeg without a shell, metadata stripping, a CSP sandbox for `/media/` on the root path.
- **Errors:** one envelope, JSON 404 and 500 with no leaks, a timeout on every outside call.
- **Code hygiene:** short functions, thin serializers, 0 TODOs, limits in settings, documented signals.
- **Telugu:** UTF-8 JSON, utf8mb4 enforced, CSV files start with a BOM, Telugu test fixtures.
- **Root-server deploy path:** the systemd sandbox, ufw, fail2ban, encrypted backups, nginx logs without query strings.

## 15. Risk and deployment considerations

- **Two deployment paths, one of them unreviewed.** Most of the repo's controls (nginx limits, header overwrite, admin allowlist, systemd sandbox, encrypted backups) live on the root-server path. Production uses the panel path. Treat production as unverified until its proxy config is reviewed, and run a read-only external check of headers, `/django-admin/` reachability and `X-Real-IP` handling with the production team.
- **qa is internet-facing with production-like accounts.** It runs `runserver` with Swagger open, IP trust on and no proxy. It should not hold real officials' passwords, or it should be closed to the public.
- **Citizen posting is open while Play Integrity is off.** That is an owner decision of 2026-11-04. Until the app is on Google Play, the system relies on per-install limits that `android_id` can evade. Record this as an accepted risk, with the mitigations in priority 3.
- **The audit log is immutable.** Fixing BE-SEC-001 stops new leaks, but removing the existing rows needs an explicit owner decision and a one-off, audited migration or command, because the model refuses deletes.
- **Database not yet chosen.** BE-COR-101 and BE-TEST-101 show behaviour that depends on collation. Add one CI run on the chosen engine as soon as the owner picks MySQL or PostgreSQL.
- **Contract impact.** Fixes for BE-ERR-101 (new 400s instead of 500s) and BE-SEC-002 (narrower citizen request list) change API behaviour. Update `docs/api-contract.md` first, and tell the mobile team and the web developer before merging.
